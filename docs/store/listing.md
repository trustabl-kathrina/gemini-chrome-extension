## Detailed description

```
Dayflow is a browser agent that does your routine web work in your own browser, with your own AI backend.

You type a task in the side panel. Dayflow opens the tab, reads the page the way you do (elements, labels, and —
if you leave Vision on — a screenshot after every action), then clicks, types, downloads and files things away,
narrating one sentence before each step so you can follow along and stop it at any point.

Two things make it yours rather than a black box:

• You own the brain. Dayflow has no server of its own. It talks only to the backend you point it at — run it on
  your laptop with one command, or deploy it to your Google Cloud project on Cloud Run. Gemini is called with
  your credentials, and your data never passes through the developer.

• You own the config. Skills (the prompts it can run), site profiles (what the agent should know about a site and
  whether to read it as DOM or as pixels), permissions (which domains it may visit, what needs your explicit OK)
  and schedules are one YAML file you can edit in the panel and sync to the brain.

The default pack is student ops, built for KBTU's portal:
• Vault sync — walk the course file tree, download what is new, save it to Google Drive under Dayflow/<course>/,
  and index every file with a summary and its deadlines.
• Courseware — turn a syllabus into a cheatsheet and a practice quiz you can open in a tab.
• Lab work — read the lab PDF, create a private GitHub repo, solve the tasks with Gemini code execution, and push
  a runnable notebook with real outputs plus a report.
• Team ops — post the week's update in a chat, open the issues and the pull request that go with it.
• Pitch deck — build a slide deck about a repository.

Safety is not an afterthought: password, card and one-time-code fields are masked before anything leaves the page;
navigation is restricted to the domains in your allow-list; sending a message, opening a pull request or running
JavaScript on a page asks you first, on a card that shows exactly what will happen; every run has a hard cap on
the number of browser actions.

Requirements: Chrome 116+, and a Dayflow brain you run yourself (setup is one command; the code, the deploy
target and the privacy policy are all in the public repository).
```

## Single purpose

```
Dayflow has one purpose: to carry out browsing tasks that the user asks for in its side panel — read the page the
user names, click and type on it, download or upload the files that task needs, and report the result. Every other
capability in the extension (settings, config, schedules, notifications) exists to configure or report on that one
activity.
```

## Permission justifications

One field per permission in the dashboard.

- **storage** — Keeps the user's own settings on the machine: backend URL and token, the skills/sites/permissions
  YAML, and the transcript of recent runs so the panel can be reopened. Nothing is stored remotely by the extension.
- **alarms** — Runs the schedules the user created in Config (for example "sync my course files every morning").
  Without alarms a scheduled skill cannot wake the service worker.
- **sidePanel** — The side panel is the entire user interface: the chat transcript, the approval cards and the
  settings/config screens live there.
- **tabs** — A task names a page ("open the portal"); the extension must create that tab, focus it, and know its
  URL and title to report progress and to enforce the domain allow-list before acting.
- **tabGroups** — Every tab the agent opens is collected in a "Dayflow" tab group (in a window of its own by
  default), so the user's own tabs and their active tab are never touched or switched while a task runs.
- **scripting** — The agent acts instead of the user: it injects the content script that lists the page's visible
  elements and performs the click/type/scroll the model asked for on the tab of the current task.
- **downloads** — Course files and other documents are obtained by triggering the page's own download and then
  reading the completed item, so the file can be saved to the user's vault (Google Drive and/or their backend).
- **notifications** — Tells the user when a scheduled run finished or failed while the side panel was closed.
- **webNavigation** — Lets the agent wait for the page it just navigated to finish loading before reading it,
  instead of acting on a half-rendered document.
- **activeTab** — Lets the user point the agent at the page already in front of them ("summarise this") without
  granting anything broader for that interaction.
- **identity** — `chrome.identity.getAuthToken` for Google sign-in, used only to obtain a Drive token with the
  `drive.file` scope so the vault can be written to the user's own Drive. No other identity use.
- **host permission `<all_urls>`** — Dayflow is a general browser agent: the sites a user will point it at are
  their own portal, LMS, tracker or messenger, and cannot be enumerated at review time. At runtime the extension
  restricts itself to the domains in the user's navigation allow-list (Settings → Config), refuses anything else
  in the panel and again in the backend, and only ever reads the tab of the task the user started.
- **Remote code** — None. The extension ships all its JavaScript in the package; no code is fetched or evaluated
  from a server. Model output is data (tool names and arguments), never code that the extension runs.

## Data use disclosures

What leaves the browser, in the dashboard's own terms:

- **Website content — collected, and used only for the item's single purpose.** During a run, the element list of
  the tab being operated on (roles, visible text, coordinates) and, when Vision is enabled, a JPEG screenshot of
  that tab are sent to the backend URL the user configured, which forwards them to Google Gemini using the user's
  own credentials. Password, card-number and one-time-code values are masked (`•••`) before they leave the page.
  Files the task downloads are uploaded to the user's Google Drive (`drive.file` scope) and/or to the user's own
  backend, so they can be parsed and indexed.
- **Personally identifiable information — not collected by the developer.** If the user signs in with Google,
  their email and display name are stored locally, in `chrome.storage.local`, and shown in Settings.
- **Authentication information — stored locally only.** The backend token and the Google OAuth access token never
  go anywhere but the backend the user chose and Google's own OAuth endpoint.
- **Not collected at all:** health, financial, personal communications the user did not ask the agent to send,
  location, web history, and user activity (clicks/keystrokes outside a run). There is no analytics or telemetry
  SDK in the package.
- **No third parties.** The developer operates no server and receives no data. GitHub, Linear and Telegram receive
  data only when the user connects them or names them in a task.

Certifications to tick, all true for this item: data is not sold or transferred to third parties except for the
approved use case; data is not used or transferred for purposes unrelated to the item's single purpose; data is not
used or transferred to determine creditworthiness or for lending purposes.
